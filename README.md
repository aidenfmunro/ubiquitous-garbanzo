# Password benchmark

Расширяемый стенд на C++20. Один эксперимент — один целевой хеш.
Алгоритмы и стратегии подключаются исходным кодом с пересборкой проекта.

Реализованы CPU-исполнитель, потоковая словарная стратегия, автоматическая
загрузка SecLists, общий CLI, MD5 и Argon2id. **Сохранение отчётов и CUDA-перебор пока
не реализованы.** MD5 здесь — учебный алгоритм для эксперимента, а не способ
хранения реальных паролей.

## Сборка и проверка

Нужны CMake >= 3.24 и C++20-компилятор со стандартной библиотекой,
поддерживающей concepts и `std::jthread`, а также `libargon2` с заголовком `argon2.h`.
Argon2id входит в каждую сборку; библиотека и заголовок обязательны.

Общие настройки заданы в `cmake/CompilerOptions.cmake` и подключаются корневым
CMake до создания целей: C++20/CUDA20 без расширений, `-Wall -Wextra -Wpedantic`
для C++-компиляции. Библиотеки, приложение и тесты наследуют эти настройки.
`-Werror` не включается.

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel
ctest --test-dir build --output-on-failure
```

Первая обычная сборка автоматически загружает словарь и требует доступа к сети.
Повторная сборка проверяет SHA-256 локальной копии и не скачивает её заново,
если она корректна. Конфигурация CMake сама по себе сеть не использует.

`ctest --test-dir build --verbose` показывает отдельные тестовые сценарии.
Чтобы отключить сборку тестов, передайте `-DBUILD_TESTING=OFF`.

CPU-сборка не требует CUDA Toolkit. Для будущих CUDA-модулей предусмотрено:

```bash
cmake -S . -B build-cuda -DPWBENCH_ENABLE_CUDA=ON
```

Эта опция только включает CUDA toolchain. Она **не добавляет GPU-исполнитель**
и не делает CPU-код переносимым на GPU. При отсутствии компилятора конфигурация
завершается ошибкой. Успешная CUDA-сборка и запуск на GPU пока не проверены.

## Запуск MD5-пайплайна

Без выбора приложение показывает справку и зарегистрированные сочетания:

```bash
./build/src/app/pwbench
./build/src/app/pwbench --help
./build/src/app/pwbench --algorithm md5 --help
```

Для запуска обязательны все три селектора и тестовый пароль:

```bash
./build/src/app/pwbench --algorithm md5 --strategy wordlist --backend cpu --password password
```

Выбора алгоритма, стратегии или backend по умолчанию нет. Один `--password`
не запускает подбор. Неполный выбор возвращает ошибку и справку; неподдерживаемое
сочетание не заменяется другим. `--help` разрешает неполный выбор как фильтр справки.

Приложение вычисляет MD5 заданного пароля, а затем передаёт подбору только
подготовленную цель. Кандидаты читаются из автоматически загруженного словаря.
По умолчанию используется один поток. Дополнительные варианты:

```bash
./build/src/app/pwbench --algorithm md5 --strategy wordlist --backend cpu --password password --threads 4
./build/src/app/pwbench --algorithm md5 --strategy wordlist --backend cpu --password example --wordlist /path/to/words.txt
./build/src/app/pwbench --help
```

Вывод содержит алгоритм, стратегию, backend, целевой хеш, статус, найденный
кандидат, число проверок и время в наносекундах. При отсутствии пароля в словаре
приложение возвращает код 1, а не ошибку исполнения. Путь к стандартному словарю
привязан к каталогу сборки; при переносе исполняемого файла используйте `--wordlist`.
Передавайте через CLI тестовые пароли: аргументы могут попадать в историю shell
и быть видны в списке процессов.

`src/md5/` содержит только реализацию алгоритма и его сборку. Точка входа —
`src/app/main.cpp`, адаптер MD5 — `src/modules/md5.cpp`, регистрация сочетаний —
`src/app/registrations.cpp`. Общий `src/app/cli.cpp` не знает имён и параметров
конкретных алгоритмов и стратегий. Реализация проверяется тестовыми
векторами RFC 1321, граничными длинами, бинарными входами и сквозными тестами CLI.

## Запуск Argon2id на CPU

Установите `libargon2` с заголовками (`brew install argon2` на macOS или
`apt install libargon2-dev` на Debian и Ubuntu). Отдельный флаг включения не нужен.
Зависимость подключается через `find_package(Argon2 REQUIRED)` и цель `Argon2::Argon2`.
Если CMake не находит библиотеку, передайте путь установки в `CMAKE_PREFIX_PATH`.
Для Homebrew этот путь показывает команда `brew --prefix argon2`.

```bash
printf 'another-fixture\nbench-fixture\n' > build/fixture.txt
./build/src/app/pwbench --algorithm argon2id --strategy wordlist --backend cpu --password bench-fixture \
  --wordlist build/fixture.txt --memory-kib 65536 --iterations 3 --lanes 1
```

`--memory-kib`, `--iterations` и `--lanes` задают параметры `m`, `t` и `p`.
Значения по умолчанию — 65 536 КиБ, 3 прохода и 1 линия. Минимум памяти на одно
вычисление составляет `8 × p` КиБ. `--threads` задаёт число потоков стенда.
Каждое одновременно выполняемое хеширование выделяет собственную рабочую память.

`target_hash` выводится в формате PHC и содержит версию, параметры, соль
и хеш. Стенд использует фиксированную публичную 16-байтную соль для повторяемых
экспериментов с синтетическими паролями. Хеш цели вычисляется перед замером.
Модуль проверяет остановку перед каждым кандидатом (`poll_interval = 1`),
а не раз в 256 проверок. Уже выполняющееся хеширование не прерывается.

## Словарь

Список автоматически сохраняется в `build/data/Most-Popular-Letter-Passes.txt`.
Отдельная команда скачивания не требуется. Повреждённый файл загружается заново;
при ошибке сети или контрольной суммы сборка завершается ошибкой.

- Источник: [SecLists / Most-Popular-Letter-Passes.txt](https://github.com/danielmiessler/SecLists/blob/08f12147a315be88a4710edd8e0246c36ed4649f/Passwords/Most-Popular-Letter-Passes.txt).
- Commit: `08f12147a315be88a4710edd8e0246c36ed4649f`.
- SHA-256: `141a1ba1d2aabcb9069481d6aaa95159a3c0268e297ecedc40a30b6613d36b60`.
- Размер: 322 069 байт, 47 603 строки.
- Исходный проект распространяется по [MIT License](https://github.com/danielmiessler/SecLists/blob/master/LICENSE).

`pwbench::WordlistStrategy` из `pwbench/strategies/wordlist.hpp` подходит любому
CPU-алгоритму стенда. Файл читается блоками по 64 КиБ; размер можно задать в
конструкторе. Блок дополняется до конца текущей строки, поэтому длинный пароль
не разбивается между заданиями. В памяти находятся только выданные блоки,
а не весь словарь. Очень длинная строка увеличивает размер соответствующего блока.

Разделители LF и CRLF удаляются; пробелы, пустые пароли и остальные байты
сохраняются. Завершающий LF не создаёт дополнительный пустой пароль. Последняя
строка без LF также обрабатывается; одиночный CR в её конце остаётся частью пароля.

## Общий слой приложения

`src/app/registrations.cpp` создаёт единственный `Registry` с фабриками
поддерживаемых сочетаний. `main()` передаёт его в `app::run()`; ни выбора через
цепочку `if`, ни отдельного реестра готовых запусков в приложении нет.

CLI понимает общие флаги `--algorithm`, `--strategy`, `--backend`, `--password`
и `--help`. Остальные значения собираются в `Parameters` — словарь строк.
`Registry::prepare(selection, request)` находит фабрику, отклоняет неизвестные
параметры и подставляет объявленные модулем значения по умолчанию. Модули
преобразуют строки в собственные типизированные конфигурации. Порядок флагов
произвольный, каждый флаг можно передать только один раз.

`--wordlist` и его стандартный путь объявляет `WordlistModule`; `--memory-kib`,
`--iterations`, `--lanes` — `Argon2idModule`; `--threads` — CPU-связывание.
Справка строится из тех же `OptionSpec`, которые используются при проверке
параметров и показывает зарегистрированные сочетания. Аргументы чужого алгоритма
или стратегии отклоняются без специальных условий в общем парсере.

Фабрика возвращает `PreparedExperiment`: `target_hash` для вывода и `Runner`
с типизированными алгоритмом, целью и конфигурацией источника во владении.
`PreparedExperiment::run(limits)` создаёт свежую стратегию и запускает исполнитель.
Исходный пароль исполнителю не передаётся. Один подготовленный эксперимент можно
запускать повторно без повторного вычисления цели.

Коды завершения: 0 — совпадение найдено или показана справка, 1 — поиск завершён
без совпадения, 2 — ошибка. При отсутствии всех селекторов выводится справка без
подготовки цели. Для запуска пустой пароль допустим, отсутствие `--password` — ошибка.

## clangd и форматирование

CMake генерирует `build/compile_commands.json`. Файл `.clangd` указывает на этот
каталог; перед открытием проекта в редакторе выполните конфигурацию CMake.
При другом каталоге сборки измените `CompilationDatabase` в `.clangd`.

Если `clang-format` доступен при конфигурации, добавляются команды:

```bash
cmake --build build --target format
cmake --build build --target format-check
```

Первая форматирует исходники, вторая проверяет их без изменений и завершается
ошибкой при нарушении стиля. Настройки в `.clang-format`: 4 пробела и лимит
100 символов. Заголовки используют include guards. Сборка библиотеки не требует
`clangd` или `clang-format`.

## Два уровня взаимодействия

```text
Управление:
  Selection + ExperimentRequest → Registry.prepare → PreparedExperiment
  PreparedExperiment.run → новый источник → CPU/CUDA-исполнитель → RunResult

Внутри CPU-исполнителя:
  Strategy.next_work() → задание во владении рабочего потока
                             ↓
              next_candidate() → hash() → matches()
```

Выбор фабрики выполняется один раз при подготовке. Фабрика и `Runner` используют
`std::function` вне цикла кандидатов. Внутри цикла используется конкретная пара
C++-типов, без виртуальных вызовов.
Алгоритм и стратегия независимы: поддерживаемые сочетания регистрируются явно.
Не зарегистрированное сочетание возвращает ошибку без подмены backend.

## Контракты CPU-модулей

### Алгоритм

Алгоритм определяет собственные `target_type` и `digest_type` и методы:

```cpp
digest_type hash(pwbench::CandidateView candidate, const target_type& target) const;
bool matches(const digest_type& digest, const target_type& target) const;
```

`target_type` содержит целевой хеш, соль и нужные алгоритму параметры.
Общей структуры со всеми возможными полями нет. Подготовка цели выполняется
до запуска исполнителя; её API определяет участник. Исходный тестовый пароль
не передаётся исполнителю отдельным аргументом.

Объект алгоритма и цель разделяются рабочими потоками только для чтения.
Методы должны быть потокобезопасными. Рабочее состояние одного вычисления
не должно храниться в изменяемых общих полях.

### Стратегия и задание

```cpp
// Стратегия:
using work_type = /* собственный перемещаемый тип задания */;
std::optional<work_type> next_work();

// Задание:
std::optional<pwbench::CandidateView> next_candidate();
```

`next_work()` вызывается последовательно под блокировкой. Он отдаёт во
владение исполнителя блок кандидатов или состояние генератора. Разные задания
обрабатываются параллельно. Одновременно удерживается не более одного задания
на рабочий поток; весь словарь заранее загружать не требуется.

`nullopt` от стратегии означает конец потока, а не временное отсутствие данных.
Пустое задание допустимо. `nullopt` от задания означает конец этого задания.

Кандидат — указатель на байты и длина, не C-строка. Нулевые байты и пустые
пароли допустимы; нормализации и преобразования кодировки исполнитель не делает.
Память кандидата должна жить до следующего `next_candidate()` этого задания
либо до его уничтожения. Задание не должно ссылаться на общий буфер источника,
который перезаписывается следующим `next_work()`.

Во внутреннем цикле исполнитель не копирует кандидатов и не выделяет для них
память. Копируется только найденный кандидат: `RunResult` владеет его байтами.
Стратегия сама отвечает за отсутствие ненужных выделений в генераторе.

### Исполнитель

```cpp
auto result = pwbench::CpuExecutor::run(
    algorithm, target, strategy, limits, cpu_options);
```

- `RunLimits`: необязательные `max_checks` и `time_limit`.
- `CpuOptions`: `threads` (по умолчанию 1) и `poll_interval` (по умолчанию 256).
- `RunResult`: причина завершения, найденный кандидат, число проверок,
  длительность и сообщение об ошибке.

Реализованы причины `found`, `exhausted`, `check_limit`, `time_limit`, `error`.
Заданная стратегия потребляется запуском; для повторения нужна новая стратегия.

## Подключение алгоритма или стратегии

Вычислительные реализации сохраняют контракты `CpuAlgorithm` и `CpuStrategy`.
Адаптеры отдельно описывают параметры и подготовку; алгоритм не включает стратегию,
стратегия не включает алгоритм. Контракт адаптера алгоритма:

```cpp
struct MyAlgorithmModule {
    using algorithm_type = MyAlgorithm;
    static constexpr std::string_view id = "my-algorithm";
    static constexpr std::size_t poll_interval = 1;

    static std::vector<pwbench::OptionSpec> options();
    static pwbench::PreparedAlgorithm<MyAlgorithm> prepare(
        pwbench::CandidateView password, const pwbench::Parameters& parameters);
};
```

`PreparedAlgorithm<MyAlgorithm>` содержит `algorithm`, собственный `target_type`
в поле `target` и строку `target_hash`. `prepare()` вычисляет цель до измерения.
`poll_interval` должен быть положительным; для MD5 используется 256, для Argon2id — 1.

Контракт адаптера стратегии:

```cpp
struct MyStrategyModule {
    using strategy_type = MyStrategy;
    using config_type = MyOwnedConfig;
    static constexpr std::string_view id = "my-strategy";

    static std::vector<pwbench::OptionSpec> options();
    static config_type parse(const pwbench::Parameters& parameters);
    static MyStrategy create(const config_type& config);
};
```

`parse()` возвращает собственную конфигурацию, а `create()` каждый раз создаёт
новый источник, не потребляя конфигурацию. Например, `WordlistModule` хранит путь,
а не открытый поток, и открывает файл при каждом запуске.

`OptionSpec` содержит `name` без `--`, `value_name` для справки, `description`
и `default_value`. Если `default_value == nullopt`, параметр обязателен; пустая
строка как значение или default допустима. Все параметры модулей имеют значение,
беззначный `--help` принадлежит CLI. Имена состоят из строчных ASCII-букв, цифр
и дефисов, не начинаются с дефиса. Общие имена `algorithm`, `strategy`, `backend`,
`password`, `help` зарезервированы. Внутри одного сочетания имена не должны
пересекаться, включая CPU-параметр `threads`. Разные алгоритмы могут независимо
объявлять одинаковые имена параметров. Числовые диапазоны проверяет сам модуль;
для положительных целых доступен `positive_parameter<Integer>()`.

Подключите библиотеку алгоритма к корневому CMake, адаптер — к
`src/modules/CMakeLists.txt`. В `src/app/registrations.cpp` включите заголовки
адаптеров и перечислите поддерживаемые сочетания:

```cpp
pwbench::register_cpu<MyAlgorithmModule, pwbench::WordlistModule>(registry);
pwbench::register_cpu<pwbench::Md5Module, MyStrategyModule>(registry);
```

Общий CLI, исполнитель и реализации существующих модулей менять не требуется.
Автоматического декартова произведения модулей нет: каждая CPU-пара явно
инстанцируется шаблоном. Это сохраняет прямые вызовы в переборе и не объявляет
несуществующие реализации для CUDA. Новые модули не регистрируются статическими
конструкторами и не загружаются через `dlopen`.

`Registry::add(selection, options, factory)` — нижний уровень регистрации.
`factory` получает `const ExperimentRequest&` и возвращает `PreparedExperiment`.
Этот контракт позволяет отдельно зарегистрировать будущую CUDA-реализацию.
Дубликаты сочетаний, некорректные идентификаторы и пустые фабрики отклоняются.
Реестр заполняется до использования; одновременное изменение не поддерживается.
Ссылка из `options(selection)` действует до изменения или уничтожения реестра.

### Владение и повторный запуск

`ExperimentRequest.password` заимствован только на время `prepare()`. Адаптеры
не должны сохранять ссылки на пароль или `Parameters`. Алгоритм, цель и конфигурация
должны быть перемещаемыми и владеть необходимыми данными. CPU-связывание помещает
их в один типизированный `shared_ptr<const State>`, который захватывает `Runner`.
Копирование `PreparedExperiment` разделяет это состояние, а не копирует цель;
цель может быть move-only. Внутри цикла кандидатов `shared_ptr` не копируется.

После подготовки можно уничтожить запрос и реестр: подготовленный эксперимент
продолжает владеть данными. Каждый `run()` создаёт отдельную стратегию и новое
состояние исполнения; найденный кандидат возвращается во владение вызывающему коду.
Состояние подготовки освобождается при уничтожении последней копии `Runner`.

Примеры адаптеров — `include/pwbench/modules/` и `src/modules/`. Независимое
расширение проверяется в `tests/module_fixtures.hpp`, `tests/app_test.cpp` и
`tests/modules_test.cpp`: новые параметры и сочетания работают без изменения CLI.

## Семантика измерений и ограничений

- Проверка засчитывается после успешного завершения `hash` и `matches`,
  включая проверку найденного кандидата. При ошибке незавершённая проверка
  не включается в счётчик.
- `elapsed` — wall-clock время внутри `CpuExecutor::run`: создание/завершение
  потоков, получение заданий, генерация, вычисления, сравнение и остановка.
  Подготовка цели, фабрики и создание стратегии (в том числе открытие файла)
  в него не входят. Чтение словаря внутри `next_work()` входит.
  Это **не чистое время хеширования**.
- `max_checks` ограничивает суммарное число проверок во всех потоках.
  Этот режим использует атомарное резервирование на каждый кандидат; без лимита
  проверки считаются локально. Такие режимы имеют разные накладные расходы.
- Ограничение времени кооперативное. Часы и сигнал остановки проверяются перед
  заданиями и через `poll_interval` кандидатов. Выполняющийся хеш, чтение источника
  и генератор не прерываются. Для медленных алгоритмов задавайте интервал 1.
- При нескольких потоках порядок завершения отличается от порядка источника.
  Возвращается одно найденное совпадение, не обязательно первое в словаре.
  Другие потоки могут успеть выполнить дополнительные проверки до остановки.
- Совпадение, обнаруженное выполняющимся вычислением, имеет приоритет над лимитом.
  Ошибка любого потока делает весь запуск ошибочным, даже если другой нашёл совпадение.
- Ошибки параметров или подготовки цели выбрасываются из `Registry::prepare()`;
  CLI сообщает их с кодом 2 без запуска исполнителя. Ошибка создания стратегии
  в `PreparedExperiment::run()` превращается в `RunResult` с причиной `error`
  и нулевыми счётчиком и длительностью. Ошибки исполнителя сохраняют выполненные
  проверки и длительность.

Тесты проверяют корректность инфраструктуры, а не измеряют производительность
MD5 или других реальных функций. Числа тестовых заглушек нельзя использовать
как результаты проекта.

## Граница будущего CUDA-backend

CUDA-реализация регистрируется отдельно с `Backend::cuda` и возвращает тот же
`RunResult` при тех же общих `RunLimits`. CPU concepts описывают именно CPU-модули;
они не требуют вызывать host-функции или использовать `std::optional` в CUDA-ядре.

CUDA-исполнитель будет владеть device-буферами и может объединять генерацию,
хеширование и сравнение в одном ядре. `CandidateView` — простой указатель и размер;
указатель CPU нельзя считать доступным на GPU автоматически. Передача данных,
device-реализации и обработка ошибок CUDA остаются работой будущего backend.
